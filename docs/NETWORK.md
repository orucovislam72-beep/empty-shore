# Сеть (заготовка)

Мультиплеер начинается на **этапе 4**. До этого игра полностью работает офлайн. Документ — заготовка, решения ещё не приняты.

## Требования из `AGENTS.md`
- Авторитетный сервер: клиент присылает ввод и намерения; движение, урон, добычу, строительство и инвентарь считает сервер.
- Выделенный сервер — этот же проект, экспорт headless под Linux. На старте 10–30 игроков.
- High-Level Multiplayer Godot (ENet), 20 Гц, интерполяция и предсказание движения на клиенте, компактные сообщения, версия протокола.
- Репликация по зоне интереса (ближние чанки). Трафик на клиента: ≤ 40 КБ/с вниз, ≤ 10 КБ/с вверх.
- Мир хранится на сервере, автосохранение, восстановление после перезапуска.
- Защита: серверная проверка скорости, дистанции, частоты действий; лимиты запросов.
- Вход гостем с локальным идентификатором, без персональных данных. Если будет чат — «Пожаловаться» и «Заблокировать».
- Плохая сеть: переподключение, индикатор задержки, мягкая деградация.

## Что уже заложено на этапе 0
- Логика (настройки, сохранения, математика ландшафта) отделена от сцен — её можно запускать на сервере без графики.
- Ввод идёт через действия InputMap; на этапе 4 поток ввода будет упакован в сообщения клиента.
- Генерация ландшафта детерминирована по seed (проверяется тестами) — сервер и клиент смогут строить один и тот же рельеф.
- Autoload `Net` пока не создан (появится на этапе 4).

## Что заложено на этапе 1
- Вся логика выживания — в `SurvivalSession` (`scripts/core/survival_session.gd`) и классах без сцен
  (`Inventory`, `Crafting`, `SurvivalStats`, `DayNightCycle`, `ResourceField`, `Deployables`). Сцена передаёт только
  намерения: `primary()` (удар/съесть/поставить), `interact()` (попить/дрова), `craft()`, `select_slot()`, перенос в инвентаре.
  На этапе 4 эти же вызовы станут сообщениями клиента, а сессия будет работать на сервере.
- Расстановка ресурсных узлов детерминирована по seed (тест) — клиент и сервер получат одинаковые индексы узлов,
  и сообщения смогут ссылаться на узел числом, а не координатами.
- Цель удара ищется геометрически (луч + сфера), без физики — сервер сможет проверить удар той же функцией
  с проверкой дистанции.
- Состояние для сохранения уже сериализуется компактно (только изменённые узлы) — тот же формат пригоден для
  первичной синхронизации зоны интереса.

## Решения, которые будут предложены перед этапом 4 (в двух вариантах)
1. Транспорт и сериализация: RPC Godot с `PackedByteArray` против `MultiplayerSynchronizer`/`MultiplayerSpawner`.
2. Модель синхронизации движения: снимки состояния с интерполяцией против детерминированного ввода с откатом.
3. Хранение мира на сервере: файлы чанков против встроенной БД (например, SQLite через расширение — проверить лицензию).
